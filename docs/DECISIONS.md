# Decisions

Журнал архитектурных и продуктовых решений. Здесь фиксируем не только что решили, но и почему.

## 2026-06-27 — Переход к модели данных Practice

Решение: описывать практики как объекты `Practice`, а не строить интерфейс вокруг прямого чтения аудиофайлов.

Почему:

- проект должен развиваться в личную платформу развития, а не оставаться каталогом файлов;
- у практики появляются смысловые поля: контекст, описание, теги, тип контента, медиа;
- в будущем источник данных можно заменить на Supabase, API, CMS или админку.

## 2026-06-27 — Локальный файл данных как первый источник

Решение: на этапе v2 хранить практики в `src/data/practices.ts`.

Почему:

- это быстрее и безопаснее для MVP;
- не нужна авторизация, база данных и админка;
- типизированные данные уже дают архитектурную основу для будущего переноса.

## 2026-06-27 — Интерфейс разделен на компоненты

Решение: вынести UI в `src/components`.

Текущие компоненты:

- `Header`;
- `Footer`;
- `ContextSelector`;
- `SearchBar`;
- `PracticeCard`;
- `PracticeList`;
- `PracticePlayer`.

Почему:

- `page.tsx` должен быть коротким и понятным;
- компоненты легче развивать по отдельности;
- будущие поиск, фильтры, избранное и история не должны превращать страницу в большой файл.

## 2026-06-27 — Добавлен сервисный слой

Решение: создать `src/services/practice.service.ts`.

Текущие методы:

- `getAll()`;
- `getById(id)`;
- `getByContext(contextId)`;
- `getContexts()`.

Почему:

- интерфейс не должен зависеть от конкретного файла данных;
- позже можно заменить `src/data/practices.ts` на Supabase, API или другой источник;
- компоненты останутся стабильными при смене хранилища.

## 2026-06-27 — Supabase пока не подключаем

Решение: не подключать Supabase на текущем этапе.

Почему:

- MVP уже работает локально;
- сначала нужно стабилизировать модель данных и интерфейс;
- раннее подключение внешнего сервиса усложнит отладку и развитие.

## 2026-06-27 — Админку пока не делаем

Решение: не создавать `/admin` до стабилизации модели и пользовательского интерфейса.

Почему:

- админка зависит от окончательной структуры `Practice`;
- сначала нужен сервисный слой и понятный поток данных;
- ручное редактирование данных допустимо на ранней v2-стадии.
